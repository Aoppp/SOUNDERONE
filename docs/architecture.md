# 技术架构与决策

## 目标和范围

首期目标是用一个核心 Agent 服务承接多平台消息，保持回答有据可查、风险可控、对话可审计，并为人工客服提供完整上下文。问卷显示抖音咨询占 70%–80%，售后约占 60%，因此真实对接优先顺序建议为抖音、淘宝/天猫、京东、拼多多，再扩展其余平台。

本期不冒充已完成的能力包括：真实平台授权和回调、退款/补发/改订单、旺店通查询、CRM、生产工单、正式知识库与生产级数据持久化。这些都需要凭证、接口文档或业务资料。

## 请求链路

```text
平台 webhook
  -> 平台验签与字段适配
  -> 统一 IncomingMessage
  -> 前置风险策略（红线、个人信息、售后）
  -> 知识检索与可信度门槛
  -> LLM 基于检索内容生成
  -> 后置禁用词/功效声明检查
  -> 平台回复或转人工
  -> 会话与决策审计
```

## 关键设计

- 平台隔离：每个平台只负责验签、解析、回复序列化和调用平台发信 API，业务逻辑不复制。
- 知识有据：低于阈值不调用模型回答，直接转人工；回复保留文档 ID 和分数。
- 纵深防护：前置规则、检索门槛、模型指令和后置词检共同限制幻觉与违规承诺。
- 权限最小化：AI 目前没有订单写权限。将来接入订单查询也应先只读，并对敏感字段脱敏。
- 安全接入：统一入口具备共享密钥保护和消息幂等骨架，管理接口单独鉴权；正式适配器仍需实现各平台的非对称验签与重放保护。
- 人机协作：转人工事件带原因、风险标签和历史对话。当前 API 可读取完整上下文。
- 可替换基础设施：接口边界允许把 JSON 检索替换为 pgvector，把内存会话替换为 PostgreSQL。

## 生产拓扑建议

- API：FastAPI 多副本，网关层 TLS、WAF、IP/速率限制。
- 数据：PostgreSQL 存会话、消息、工单和审计；pgvector 存知识向量；Redis 做幂等、锁和限流。
- 任务：异步 worker 处理知识入库、平台重试、质检和报表。
- 可观测性：结构化日志、trace ID、错误监控、延迟/转人工率/无答案率/引用命中率指标。
- 安全：密钥进入 Secret Manager；敏感字段不写日志；按平台设置数据保留和删除策略。

## 验收门槛

- 红线用例 100% 转人工，不触发写操作。
- 标准 FAQ 回答必须包含来源，业务抽检准确率达到约定阈值后才开放自动发送。
- 未知问题、低置信度、禁用声明安全降级。
- webhook 幂等、验签、重放保护和平台限流在真实平台上线前完成。
- 人工能看到完整对话、转接原因、命中的知识来源。
